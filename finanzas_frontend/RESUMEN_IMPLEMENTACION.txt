RESUMEN DE IMPLEMENTACION - FRONTEND FINANZAS
================================================
Fecha: 2026-09-16
Alcance: creación desde cero de finanzas_frontend/, conectado en vivo a
finanzas_backend/ (Django + DRF, JWT, 23 endpoints en 7 módulos).


1. DECISIONES DE ARRANQUE (confirmadas con el usuario)
-------------------------------------------------------
- Ubicación: finanzas_frontend/, carpeta hermana de finanzas_backend/,
  dentro de proyecto_finanzas/.
- Lenguaje: TypeScript (no JavaScript) — para poder generar tipos
  automáticamente desde el OpenAPI del backend y detectar errores de
  integración en tiempo de compilación en vez de en runtime.
- Gestor de paquetes: pnpm.
- Librería de componentes: shadcn/ui sobre Tailwind CSS v4 (en vez de
  Tailwind a mano o una librería de componentes cerrada tipo Mantine).


2. PROBLEMAS DE ENTORNO ENCONTRADOS Y RESUELTOS
-------------------------------------------------------
- Node del sistema era v12.22.12 (con npm roto: "Cannot find module
  'node:path'"), incompatible con Vite. Se detectó que ya había `nvm`
  instalado pero sin ninguna versión moderna descargada.
  Solución: `nvm install --lts` (instaló Node 24.21.0), `nvm alias
  default 24` para que quede como versión por defecto del usuario.
  Se agregó un archivo `.nvmrc` con "24" en la raíz del frontend para
  que cualquier `nvm use` futuro en esa carpeta resuelva la versión
  correcta automáticamente.
- pnpm no estaba instalado: se activó vía corepack
  (`corepack enable && corepack prepare pnpm@latest --activate`).
- IMPORTANTE: cada terminal nueva NO hereda automáticamente el Node 24
  (nvm no está enganchado al arranque de shell no interactivo en este
  entorno). Hay que correr, en cada sesión de terminal nueva:
      export NVM_DIR="$HOME/.nvm" && source "$NVM_DIR/nvm.sh" && nvm use 24
  o simplemente `nvm use` parado en finanzas_frontend/ (usa el .nvmrc).


3. CÓMO SE CONECTA EL FRONTEND AL BACKEND (lo más importante)
-------------------------------------------------------
3.1. Sin configurar CORS en el backend
   En vez de tocar Django para permitir peticiones cross-origin desde
   localhost:5173, se configuró un proxy de desarrollo en
   vite.config.ts: todo lo que el navegador pide a "/api/*" en el
   puerto 5173 lo reenvía Vite internamente a http://localhost:8000.
   Para el navegador, front y back son el mismo origen. Esto es solo
   para `pnpm dev`; en producción, si el front no queda detrás del
   mismo dominio/reverse proxy que el back, hay que definir
   VITE_API_BASE_URL con la URL completa del backend (ver .env.example)
   y ahí sí habría que activar django-cors-headers en el backend.

3.2. Cliente HTTP tipado, generado desde el propio backend
   - Se corrió `openapi-typescript ../finanzas_backend/docs/openapi.json
     -o src/api/schema.d.ts` para generar automáticamente todos los
     tipos TypeScript (23 endpoints, todos los schemas: Usuario,
     Ingreso, Gasto, ServicioFijo, PlanFinanciero, AlertaPago,
     CategoriaGasto, NivelPrioridad, etc.) a partir del spec real del
     backend. No hay un solo tipo de request/response escrito a mano.
   - Se agregó el script `pnpm gen:api` en package.json para volver a
     generarlos cuando el backend cambie (documentado en el README).
   - El cliente en sí (src/api/client.ts) usa la librería `openapi-fetch`
     (no axios — se instaló axios primero y después se reemplazó, para
     no mantener dos formas distintas de tipar llamadas a la API).

3.3. Autenticación JWT (siguiendo el flujo de docs/API_REFERENCE.md)
   - Login (`POST /api/usuarios/login/`) y Registro
     (`POST /api/usuarios/registro/`) devuelven {usuario, access, refresh}.
   - `access` se guarda SOLO en memoria (store de zustand,
     src/stores/auth-store.ts) — nunca toca localStorage, para reducir
     superficie de ataque ante XSS.
   - `refresh` se persiste en localStorage para sobrevivir a que el
     usuario cierre y reabra la pestaña.
   - src/lib/jwt.ts decodifica el `exp` del JWT (sin librerías, solo
     parseando el payload base64) para saber si el access token está por
     vencer.
   - El middleware de openapi-fetch (src/api/client.ts):
       * Antes de cada request (salvo a /api/usuarios/*): si no hay
         access en memoria, o si el que hay vence en menos de 10s,
         pide uno nuevo a POST /api/usuarios/token/refresh/ ANTES de
         mandar la petición original (refresh proactivo, no reactivo:
         evita la complejidad de "reintentar" una request ya enviada,
         que con streams de body es frágil).
       * Las llamadas de refresh en paralelo se deduplican (una sola
         promesa compartida) para no disparar 10 refresh simultáneos si
         hay 10 queries pidiendo datos a la vez al cargar una página.
       * Si igual llega un 401 (refresh también vencido/inválido), se
         limpia la sesión (clearSession) y como ProtectedRoute está
         suscrito al store, la UI redirige sola a /login.
   - Esto se probó de punta a punta con un navegador real (ver sección
     7): registro -> recargar la página -> la sesión sigue viva porque
     el refresh token en localStorage renueva el access solo, sin pedir
     la contraseña de nuevo.

6. UN PROBLEMA DE DISEÑO DEL BACKEND Y CÓMO SE LO ESQUIVÓ
-------------------------------------------------------
El backend reutiliza el mismo serializer de Django para leer y para
escribir en varios endpoints (CategoriaGasto, Ingreso, ServicioFijo,
Gasto, PlanFinanciero). Como consecuencia, el OpenAPI generado
(drf-spectacular) describe el body de un POST con el mismo schema que
la respuesta, incluyendo campos que en la práctica son de solo lectura
(id, usuario_id, activo, servicio_fijo_id) como si fueran obligatorios
en el body de creación.

Esto NO se arregló en el backend (no se tocó una sola línea de
finanzas_backend/ en toda esta sesión). Se resolvió del lado del
frontend en cada features/<módulo>/api.ts:
  - Se define un tipo de input real con
    `Omit<SchemaCompleto, 'id' | 'usuario_id' | ...>` que refleja lo
    que el body realmente necesita (así los formularios están bien
    tipados y no dejan mandar campos de más).
  - Al momento de llamar a `api.POST(...)`, como el tipo que exige
    openapi-fetch es el schema completo (por la reutilización de
    arriba), se hace un cast explícito (`body as SchemaCompleto`) con
    un comentario que documenta por qué. Es un ajuste acotado al punto
    exacto donde el schema generado no es preciso, no una excepción
    generalizada al tipado.

Si en algún momento se separan los serializers de lectura/escritura en
el backend, este cast deja de hacer falta y se puede borrar sin tocar
el resto del código (los tipos de Input ya están correctos).
