================================================================================
CÓMO ABORDAR UN MÓDULO — ORDEN DE TRABAJO PASO A PASO
================================================================================
Guía de método: por dónde empezar, en qué orden seguir y cuándo dás un
módulo por terminado. Aplica a usuarios, ingresos, servicios_fijos,
gastos, planes_financieros y alertas (catalogos ya está resuelto y es la
referencia).

Regla de oro (dirección de dependencias en arquitectura hexagonal):

        domain  <──  application  <──  infrastructure
                            ^                 ^
                            └──── interfaces ─┘

    domain no importa NADA. application importa domain (los puertos).
    infrastructure implementa los puertos. interfaces pega todo.

    => Trabajás EN EL SENTIDO DE LAS FLECHAS: primero lo que no depende
       de nada, al final lo que depende de todo. Así cada capa que
       escribís solo usa cosas que ya funcionan y ya testeaste.

Traducción a "por dónde empiezo":
    1º  domain/entities.py + domain/exceptions.py   (Python puro)
    2º  domain/ports/repositories.py                (LEER, ya está escrito)
    3º  tests/domain/                               (rápido, sin DB)
    4º  tests/application/  -> el repositorio FALSO
    5º  application/use_cases/                      (Python puro)
    6º  infrastructure/models.py                    (recién acá aparece Django)
    7º  infrastructure/repositories.py              (_a_entidad primero)
    8º  infrastructure/admin.py
    9º  tests/infrastructure/                       (necesita Postgres)
    10º interfaces/api/serializers.py
    11º interfaces/api/views.py
    12º interfaces/api/urls.py                      (ya está, ajustar rutas)
    13º config + migraciones + (apps.py ready si hay eventos)
    14º manage.py check + runserver + probar endpoints

NO empieces por models.py ni por makemigrations. NO empieces por las
views. El porqué está en la sección "ERRORES DE ORDEN COMUNES".


================================================================================
FASE 0 — ENTENDER EL MÓDULO (10–15 min, sin escribir código)
================================================================================
[ ] Leé modules/<modulo>/README.md          -> qué posee el módulo
[ ] Leé modules/<modulo>/SOLUCION.txt        -> cómo resolver cada TODO + el porqué
[ ] Abrí finanzas_db/schema_finanzas.sql y localizá:
      - la tabla de la entidad (columnas, CHECK, DEFAULT)
      - los índices y constraints UNIQUE que la tocan
      - las VISTAS y queries comentadas que la usan (A–E al final del .sql)
[ ] Anotá la LISTA DE CASOS DE USO a entregar (están en application/use_cases/).
    Esa lista es "el requerimiento". Todo lo demás existe para que esos
    casos de uso funcionen.

Salida de la fase: sabés qué métodos de entidad, qué puertos y qué
consultas SQL vas a necesitar.


================================================================================
FASE 1 — DOMINIO   (domain/)   ·   sin Django, sin base de datos
================================================================================

PASO 1.1 — domain/entities.py
-----------------------------
Los CAMPOS ya están (mapean la tabla). Implementá los MÉTODOS.
Para cada método preguntate:

    ¿La entidad puede responder esto mirando SOLO sus propios atributos
    (más, como mucho, un parámetro que le paso)?
        SÍ  -> va acá, en la entidad.
        NO  -> necesita ver a "sus hermanos" o consultar la base
               -> NO va en la entidad, va en un caso de uso.

    Ejemplo resuelto en catalogos: CategoriaGasto.es_global() SÍ (mira
    self.usuario_id). NivelPrioridad.es_prescindible() NO (necesita ver
    todos los niveles) -> se eliminó de la entidad y vive en el futuro
    SimularModoEmergenciaUseCase.

PASO 1.2 — domain/exceptions.py
-------------------------------
Agregá las excepciones de negocio que van a lanzar tus casos de uso
(EmailYaRegistrado, MontoInvalido, PagoDeServicioDuplicado, ...).
Podés volver a este archivo cuando escribas los casos de uso y descubras
que falta alguna. Todas heredan de la excepción base del módulo
(<Modulo>Error).

PASO 1.3 — domain/ports/repositories.py   (SOLO LEER)
----------------------------------------------------
Ya está escrito como interfaz ABC. Es EL CONTRATO entre tu dominio y el
mundo exterior. No lo implementás acá.
    - Leé cada método y su docstring (traen el SQL equivalente).
    - Si más adelante, escribiendo un caso de uso, necesitás un método
      que no existe -> lo AGREGÁS ACÁ PRIMERO (firma + docstring con el
      SQL), y recién después lo implementás en el adapter. El dominio
      DECLARA lo que necesita; no acepta lo que la base ofrece.

PASO 1.4 — tests/domain/test_entities.py
----------------------------------------
Reemplazá los self.skipTest(...) por asserts reales. Es lo más barato de
testear (Python puro, milisegundos).

    uv run python -m unittest modules.<modulo>.tests.domain.test_entities -v

HITO FASE 1: todos los tests de dominio en verde.


================================================================================
FASE 2 — APLICACIÓN   (application/)   ·   todavía sin Django, sin base
================================================================================

PASO 2.1 — el REPOSITORIO FALSO   (en tests/application/test_use_cases.py)
------------------------------------------------------------------------
Antes que los casos de uso, completá la clase Repositorio<Entidad>Falso:
implementa el MISMO puerto que el repo Django real, pero respaldado por
una lista de Python. Patrón (usar dataclasses.replace para asignar id):

    from dataclasses import replace
    def crear(self, x):
        creado = replace(x, id=self._siguiente_id)
        self._items.append(creado); self._siguiente_id += 1
        return creado

Este doble es lo que te deja testear los casos de uso SIN Postgres.

PASO 2.2 — application/use_cases/  ·  UNO por vez, en loop rojo→verde
-------------------------------------------------------------------
Por cada archivo de use_cases/:
    a) escribí (o ajustá) su test en test_use_cases.py usando el repo falso
    b) implementá ejecutar()
    c) corré el test hasta verde
    d) si necesitás un método de puerto nuevo o una excepción nueva ->
       volvé a FASE 1 (pasos 1.2 / 1.3), agregalo, seguí.

Forma típica de un caso de uso (mirá crear_categoria_personalizada.py):
    1. validar reglas de negocio -> lanzar excepción de dominio si fallan
    2. construir la entidad (sin id)
    3. delegar en el repositorio (self.repositorio.xxx(...))
    4. (si aplica) publicar un evento de dominio

Casos de uso que CRUZAN módulos (CalcularBalanceMensualUseCase,
CompararPlanVsRealUseCase, SimularModoEmergenciaUseCase,
GenerarAlertasDeVencimientoUseCase): reciben los puertos de OTROS módulos
por inyección (son interfaces, no implementaciones) -> en el test usás un
segundo repo falso. Sigue siendo Python puro.

    uv run python -m unittest discover -s modules/<modulo> -p "test_*.py" -v
    (van a fallar/skipear solo los de infrastructure; el resto en verde)

HITO FASE 2: dominio + aplicación en verde, sin haber tocado Django.


================================================================================
FASE 3 — INFRAESTRUCTURA   (infrastructure/)   ·   acá entra Django + Postgres
================================================================================

PASO 3.1 — infrastructure/models.py
-----------------------------------
Mapeo 1:1 con la tabla del schema:
    - db_table = "<tabla>"  ·  managed = False   (la tabla ya existe en el .sql)
    - campos con el mismo tipo/nulabilidad que el CREATE TABLE
    - Meta.indexes / Meta.constraints reflejando índices y UNIQUE del .sql
    - FK a OTRO módulo: decidí -> ForeignKey("app.Modelo", db_column=...)
      (fiel al schema) o IntegerField(db_column=...) (desacoplado, validás
      en el caso de uso). Está explicado en cada SOLUCION.txt.

PASO 3.2 — infrastructure/repositories.py
----------------------------------------
Implementá el puerto de FASE 1. Orden interno:
    1. _a_entidad(self, modelo) -> Entidad   PRIMERO. Es el mapeo
       ORM->dominio, el corazón del patrón. Todo lo demás lo reusa.
       Usá modelo.<fk>_id (el id plano), NO modelo.<fk> (evita una query
       extra trayendo el objeto relacionado).
    2. cada método del puerto: traducí el SQL del docstring a ORM
       (.filter, .aggregate(Sum(...)), .values().annotate(), Window/Lag...).
       Métodos de consulta que "pueden no encontrar": devolvé None / [] /
       Decimal("0"). Métodos que crean: devolvé la entidad con id via
       _a_entidad.

PASO 3.3 — infrastructure/admin.py
----------------------------------
Trivial: @admin.register(<Modelo>) con un ModelAdmin (list_display,
list_filter, search_fields). Copiá el de catalogos.

PASO 3.4 — tests/infrastructure/test_repositories.py
---------------------------------------------------
1. Completá el setUpClass: CREATE TABLE IF NOT EXISTS con un subconjunto
   MÍNIMO del DDL real (Django NO crea tablas managed=False en la base de
   test). Incluí los índices UNIQUE que quieras probar.
2. Reemplazá los skipTest por asserts.

    uv run manage.py test modules.<modulo>.tests.infrastructure   (necesita Postgres)

HITO FASE 3: el repo Django hace exactamente lo que hace el repo falso,
pero contra la base real.


================================================================================
FASE 4 — INTERFACES   (interfaces/api/)   ·   la capa más fina: pegamento HTTP
================================================================================

PASO 4.1 — serializers.py
-------------------------
serializers.Serializer SIMPLE (NO ModelSerializer). La forma la dicta la
ENTIDAD DE DOMINIO / el objeto de lectura, NO la tabla. El serializer es
parte de interfaces/ y NO debe importar nada de infrastructure/.
    - read_only para lo que la API devuelve pero no acepta (id, usuario_id...)
    - write_only para secretos que entran pero no salen (password)

PASO 4.2 — views.py
-------------------
Cada view hace SIEMPRE lo mismo (mirá modules/catalogos/.../views.py):
    1. validar el serializer de entrada  (forma)
    2. armar el caso de uso con los adapters CONCRETOS:
           CasoDeUso(repositorio=DjangoXxxRepository())
       (cross-módulo: inyectás los Django*Repository de cada módulo, o un
        caso de uso ya armado)
    3. ejecutar el caso de uso con los datos del request
    4. serializar la respuesta
    5. traducir excepción de dominio -> código HTTP
           NoEncontrado -> 404 · reglas -> 400 · duplicado/estado -> 409
           credenciales -> 401
Esta es la ÚNICA capa donde se juntan dominio + Django. Sin lógica de
negocio acá.

PASO 4.3 — urls.py
------------------
Ya está escrito. Ajustá paths solo si cambiaste nombres de endpoint.

================================================================================
[ ] config/settings/base.py: módulo en INSTALLED_APPS y en

                              (YA hecho para los 6)

       En migrate NO ejecuta DDL (la tabla ya existe). Solo registra estado.
[ ] Solo si el módulo REACCIONA a eventos (alertas): implementá

[ ] uv run manage.py check          -> "no issues"
[ ] uv run manage.py runserver      -> probar los endpoints del módulo

DEFINICIÓN DE "TERMINADO" (checklist por módulo)
================================================================================
[ ] tests/domain + tests/application en verde  (uv run python -m unittest ...)
[ ] tests/infrastructure en verde              (uv run manage.py test ...)
[ ] uv run manage.py check                     sin errores
[ ] cada endpoint: 2xx en el camino feliz y el 4xx correcto en cada error
    documentado
[ ] las consultas mapeadas de SQL verificadas contra los números del
    seed (02_seed_test_data.sql) — cada SOLUCION.txt trae los valores
    esperados (ej. marzo 2026: ingresos 1.020.000)
[ ] ningún import de infrastructure/ dentro de domain/ o application/
[ ] ningún import de Django dentro de domain/ o application/

================================================================================
EL LOOP INTERNO (lo que hacés el 80% del tiempo)
================================================================================
        escribo test (rojo)  ->  implemento  ->  test verde  ->  siguiente

    Nivel entidad:      test_entities.py  <->  entities.py
    Nivel caso de uso:  test_use_cases.py (repo falso)  <->  use_cases/*.py
    Nivel repo:         test_repositories.py (DDL en setUpClass)  <->  repositories.py

Si para pasar un test necesitás algo que no existe (un método de puerto,
una excepción): subís una capa, lo agregás en domain/, bajás y seguís.
NUNCA al revés (no agregues métodos de puerto "porque el ORM los permite").


================================================================================
ERRORES DE ORDEN COMUNES (y por qué duelen)
================================================================================
- Empezar por models.py + makemigrations:
  terminás reescribiendo el modelo 2–3 veces a medida que el dominio se
  aclara. El modelo es consecuencia del dominio, no al revés.

- Escribir las views antes que los casos de uso:
  se te filtra lógica de negocio en la view (validaciones, cálculos).
  La view tiene que quedar tonta: validar, delegar, serializar.

- Implementar el repo Django real antes que el repo FALSO:
  no podés testear los casos de uso en aislamiento -> terminás
  necesitando Postgres para probar lógica que es Python puro.

- Agregar métodos al puerto desde infrastructure/:
  invertís la dependencia. El puerto lo define el dominio según lo que
  NECESITA; el adapter se adapta a eso.

- Serializers como ModelSerializer apuntando al *Model:
  rompe en runtime (espera la relación `usuario`, la entidad solo tiene
  `usuario_id`) y acopla interfaces/ con infrastructure/. Ver el README
  de catalogos, punto 5.

- Dejar tests/ para el final:
  perdés el feedback rápido. Los de domain/application corren en
  milisegundos sin Docker; usalos como red mientras escribís.


================================================================================
ORDEN SUGERIDO ENTRE MÓDULOS  (del README del proyecto)
================================================================================
    ingresos  ->  servicios_fijos  ->  gastos  ->  planes_financieros
              ->  alertas  ->  usuarios

  - ingresos: el más simple, para agarrar el patrón (poca regla).
  - servicios_fijos: suma lógica de fechas en la entidad.
  - gastos: el más grande (balance, variación/LAG, modo emergencia,
    evento). Hacelo cuando ya tengas el patrón aceitado.
  - planes_financieros: regla de entidad (suma 100) + índice único parcial.
  - alertas: máquina de estados + suscripción al evento de gastos
    (depende de que gastos ya publique GastoRegistrado).
  - usuarios: al final. Varios módulos solo lo necesitan como FK
    (hoy apuntan a auth_user). Ver CONFIGURACION_FUNCIONAL.txt sección 5.

DÓNDE ESTÁ LA PARTE DIFÍCIL DE CADA MÓDULO (dónde ir más despacio):
    usuarios          -> application (hash inyectado) + decisión AUTH_USER_MODEL
    ingresos          -> ninguna, es el calentamiento
    servicios_fijos   -> domain (fecha_vencimiento_en, debe_generar_alerta)
    gastos            -> application (LAG, balance, modo emergencia) +
                         infra (values().annotate(), Window/Lag)
    planes_financieros-> application (activar: desactivar→activar + atomic)
    alertas           -> domain (máquina de estados) + cableado
                         (apps.py ready + EventBus de shared/)

RESUMEN EN UNA LÍNEA
================================================================================
Entidad -> (tests) -> puertos (leer) -> repo FALSO -> casos de uso ->
(tests) -> models -> repo Django (_a_entidad primero) -> (tests) ->
serializers -> views -> urls -> config/migraciones -> check -> probar.
De adentro hacia afuera, testeando en cada capa antes de pasar a la siguiente.
